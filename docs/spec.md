# ローカルLLMモデル性能検証 仕様書

このファイルは**検証の設計仕様書**です。「なぜそう測るか・なぜその基準にしたか」を確認・見直すために読んでください。実行方法は`README.md`を、エージェントが辿る工程は`.claude/skills/benchmark-run/SKILL.md`を参照してください。

対象モデル: `gemma4:26b` / `qwen3-coder:30b` / `qwen3.8:27b`

---

## 検証する4つの軸

| 軸 | 何を測るか | 測定方法 | 実施者 |
|---|---|---|---|
| **軸1: 生成速度** | 1秒あたりの生成トークン数(tokens/sec) | `./bin/sweep.sh`が固定プロンプトで自動計測する`eval rate`の平均 | エージェント |
| **軸2: 実用的なコンテキスト上限** | そのモデルが100% GPUを維持できる最大のコンテキスト長 | 同スクリプトが`OLLAMA_CONTEXT_LENGTH`を4段階変えながら`ollama ps`の`PROCESSOR`列を自動記録 | エージェント |
| **軸3: ツール呼び出し精度** | 調査の**過程**(どうやって調べたか): ツール選択・構文エラー・幻覚・完結性 | タスク1〜3実行時のツール呼び出しログ(`results/traces/`)を採点基準(0〜5点)で採点 | エージェント(人間は結果の妥当性を確認) |
| **軸4: コード調査の精度** | 調査の**結論**(最終的な回答が合っているか) | タスク1〜3の最終回答のみを、事前に用意した正解セットと突き合わせて採点(0〜5点) | エージェント(人間は結果の妥当性を確認) |

1. **軸2が重要な理由**: VRAM(実測28.1GiB)を超えるとモデルの一部がCPUにはみ出し、速度が激減する。実際に`qwen3-coder:30b`でコンテキスト長262144を指定した際は12%がCPUに溢れ、97.1 → 9.4 tokens/secと約1/10まで低下した。つまり「コンテキスト長は大きいほど良い」のではなく、**GPUに収まる範囲での最大値**を見つける必要がある。
2. **軸1と軸2は同時に測る**: 両者は密接に関係するため、`bin/sweep.sh`が1回の実行の中でコンテキスト長を変えながら`ollama ps`(軸2)と速度(軸1)の両方をまとめて記録する。
3. **軸1・2と軸3・4で測定方法が分かれる理由**: 軸1・2はOllama単体で機械的に測定できるため`ollama run`を直接叩いて完結する。一方、軸3・4はClaude Code上で実際のコード調査タスクを解かせる必要があるため、`bin/run-tasks.sh`が`claude -p`でfixture/内にセッションを立てて実行する。
4. **各軸の詳細**: タスク1〜3の具体的な型、二軸それぞれの採点基準は本ファイル後半の各セクションを参照。スコアの記録先は`results/scores.tsv`(`bin/score.sh`が追記)、確定した結果と考察は`reports/`配下の日付入りレポートにある。

## モデルごとの設定値: 値の決め方の方針

各モデルに与える具体的なコンテキスト長は`bin/lib/common.sh`のモデルテーブルが持つ(スクリプトが自動で解決するため、どこかに転記する必要はない)。その値の実測根拠は`reports/`配下の日付入りレポートにある。ここではその値をどう決めたかの方針だけを述べる。

各モデルには「そのモデルが100% GPUを維持できる最大のコンテキスト長」を与える。全モデルを同じ値に揃える案もあるが、コンテキスト長の余裕は実運用における本物の優位性(auto-compactが発火しにくく、長い調査でも情報が失われにくい)であるため、「実際に採用したときの性能」を比較する本検証の目的には、各モデルのベストを引き出す方が適切と判断した。

## 軸3・4共通: タスクの型(実プロダクトの実クラス名に置き換えて使用)

軸3(ツール呼び出し精度)と軸4(コード調査の精度)は、**同じ3つのタスクの実行結果を、異なる観点で2回採点する**(調査の過程を見るか、最終的な結論を見るか)。「あるメソッドの呼び出し元を列挙」と「変更の影響範囲を特定」という2つのタスクは内容が重複しやすいため、軸ごとに別のタスクを用意するのではなく、1回の実行を2軸で採点する設計にしている。

| # | タスクの型 | 正解セットの作り方 |
|---|---|---|
| タスク1 | 「指定クラスの指定メソッドを呼び出している箇所をすべて列挙して」 | `rg`で機械的に正解セットを事前生成する |
| タスク2 | 「指定箇所(プロパティや引数の型など)を変更した場合に影響を受けるファイル・テストを特定して」 | 実際に変更してテストを実行し、影響範囲を確認しておく |
| タスク3 | 「特定のテスト失敗の原因をコードから特定して」 | 人間が事前にコードを読み、原因を把握しておく |

本リポジトリで実際に使うタスク文面は`tasks/tasks.md`、正解セットは`answers/answers.md`にある。実プロダクトのクラス名に置き換えて使う場合の扱いは後述の「機密情報の分離ルールと根拠」を参照。

### 参考タスク(コアの3タスクには含めない)

「指定クラスの責務を1〜2文で要約して」というタスクの型は、正解が主観的で採点基準を揃えにくいため、コアの3タスクからは外している。ただし、検索能力ではなく読解・要約能力を見たい場合の**オプションのタスク**として、必要であれば追加で実施してよい(その場合も採点は参考値扱いとし、合計点には含めない)。

## 軸3: Claude Codeのツール呼び出し精度(調査の過程を見る)

タスク1〜3実行時の**ツール呼び出しログ**を採点対象とする(最終的な回答の正誤は見ない。それは軸4の役割)。採点手順は`.claude/skills/benchmark-score/SKILL.md`を参照。

### 採点基準(1タスクにつき0〜5点)

| 観点 | 配点 |
|---|---|
| 適切なツールを選択できたか(Grepで済む場面でBashの`cat`を多用する等の非効率がないか) | 2点 |
| ツール呼び出しの構文・形式エラーが無かったか | 1点 |
| 存在しないファイルパス・シンボルを幻覚(hallucination)しなかったか | 1点 |
| 途中で諦めず、調査を完結させて結論に到達したか | 1点 |

> **設計上の注記**: 軸3の採点基準には「最終的な回答が正しかったか」を含めていない。これは軸4そのもの(結論の正誤)を測る項目であり、軸3にも含めると同じことを二重に計測してしまうため。

**実行回数について**: 各タスクは原則1回のみ実施する(一発勝負の評価)。ローカルLLMは同一プロンプトでも出力が揺れるため、スコアが僅差で判断に迷う場合のみ同一タスクを2回実施し、平均を採る。全モデルで同じ回数・同じ条件を適用すること。

## 軸4: コード調査の精度(最終的な結論を見る)

タスク1〜3の**最終回答のみ**を採点対象とする(調査の過程・ツール選択の巧拙は見ない。それは軸3の役割)。採点手順は`.claude/skills/benchmark-score/SKILL.md`を参照。

### 採点基準

正解セットとの一致度で0〜5点(全部正解=5、一部欠落/誤り=部分点、完全に誤り=0)。

**実行回数について**: 各タスクは原則1回のみ実施する(一発勝負の評価)。ローカルLLMは同一プロンプトでも出力が揺れるため、スコアが僅差で判断に迷う場合のみ同一タスクを2回実施し、平均を採る。全モデルで同じ回数・同じ条件を適用すること。

## 採点フェーズの設計根拠

タスクの実行(`bin/run-tasks.sh`)と採点(`benchmark-score` Skill)を分離しているのは、以下の理由による。

- モデルごとに採点の甘さがぶれると、比較が不公平になる
- 実行と採点を分けると、全モデルの回答を**同一の採点者・同一基準**でまとめて採点できる

(実際の採点手順は`.claude/skills/benchmark-score/SKILL.md`を参照)

### ブラインド採点の設計根拠: なぜサブエージェントに任せられるのか

サブエージェントは**まっさらなコンテキストで起動する**ため、自分がその調査を行った記憶を持たない。「回答」と「正解セット」(または「トランスクリプト」)だけを渡されて突き合わせる、実質的にブラインドの採点者・集計者になる。自分の推論を擁護するバイアスが働かない。ファイル名からモデル名を伏せているため、「どのモデルの回答か」による先入観も入らない。

### 軸3と軸4で採点の難しさが異なる

軸4は正解セットとの集合の突き合わせという機械的な作業で、元の調査タスクよりはるかに簡単なため、採点結果を信頼できる。一方、軸3の「ツール選択が適切だったか」は判断を要するため、`results/traces/`のイベントストリームから事実(ツール呼び出し回数・エラー件数・幻覚の有無)を抽出した上で採点基準に当てる、という2段構えで採点する。

| 軸 | 採点の性質 | 人間の役割 |
|---|---|---|
| 軸4 | 正解セットとの機械的な突き合わせ | スコアが実測値と整合しているか確認する |
| 軸3 | 事実の抽出(機械的)＋採点基準の適用(判断を要する) | 同左。特に軸3は判断が入るため、減点理由が妥当かを確認する |

採点手順は`.claude/skills/benchmark-score/SKILL.md`にある。

## 軸1: 生成速度(tokens/sec)

**最新の実測値は`reports/`配下の日付入りレポートにある。** この節は量子化形式との
関係を見るための参考値で、値そのものの正典はレポート側である(同じ数値を2箇所で
持つと必ず片方が古くなるため、ここでは更新しない)。

| モデル | 量子化/形式 | tokens/sec | 条件 |
|---|---|---|---|
| gemma4:26b | Q4_K_M, GGUF/llama.cpp | 73.9〜79.4 | 32768〜262144の全段で100% GPU |
| qwen3-coder:30b | Q4_K_M, GGUF/llama.cpp | 97.1 | ctx=131072, 100% GPU |
| qwen3.6:27b-mlx | nvfp4, MLX | 23.4 | **検証対象から除外済み**。nvfp4はMLXネイティブの量子化行列演算カーネルが無く(int4/int8のみ高速化対象)、ロード時にdequantizeされ実質フル精度相当で動作するため、3モデル中最も遅く評価前から負けが確定していた。除外後の代わりは`qwen3.8:27b`(詳細は下記「`qwen3.8:27b`を追加した理由と評価上の注目点」を参照)。この知見(nvfp4×MLXの相性問題)自体は今後のモデル選定でも再利用価値があるため記録として保持する |

## 軸1・2の測定値の読み方

`bin/sweep.sh`が生成する結果ファイル(`results/benchmark-results-<日時>.md`)を読み解くための背景知識。

### `ollama ps`の出力

```
NAME              ID              SIZE     PROCESSOR    CONTEXT   UNTIL
qwen3-coder:30b   5571076f3d70    25 GB    100% GPU     131072    4 minutes from now
```

- `PROCESSOR`が`100% GPU`なら合格(そのコンテキスト長はVRAM予算内)。これが軸2の判定そのものである
- `xx% CPU / yy% GPU`と出たら溢れている。溢れた場合も速度は記録し、「溢れるとどれだけ遅くなるか」のデータとして扱う
- `ID`列があるため、`SIZE`は3列目である。列位置で機械的に切り出す際はここを間違えやすい

### `ollama run --verbose`の出力

2026-08-25、`qwen3-coder:30b`で確認:

```
total duration:       8.056091333s
load duration:        7.720224625s
prompt eval count:    9 token(s)
prompt eval duration: 42.446ms
prompt eval rate:     212.03 tokens/s
eval count:           29 token(s)
eval duration:        280.437ms
eval rate:            103.41 tokens/s   ← 軸1として記録する値
```

`eval rate`がそのままtokens/secになる(curl/jqによる計算は不要)。

**`eval rate`(速度)と`eval count`(生成量)は別物で、体感の待ち時間は両者の商で決まる。** `eval rate`だけで比較すると、寡黙なモデルと冗長なモデルの差を見落とす。

初回はモデルロード直後で`load duration`が大きいため、同じ固定プロンプトで複数回実行して初回を除いた平均を取る。この考え方は`bin/sweep.sh`の`--runs`オプション(既定4回、1回目は破棄)に反映されている。

### 1組だけ手動で確認する場合

`bin/sweep.sh`が使えない状況や、1組だけ切り出して確かめたい場合は直接測定できる。固定プロンプトは`bin/sweep.sh`の`FIXED_PROMPT`と同じものを使う(揃えないと過去の測定値と比較できない)。

```bash
ollama run <model名> "warmup"
ollama ps
ollama run <model名> "<FIXED_PROMPTと同じ文面>" --verbose
```

## `qwen3.8:27b`を追加した理由と評価上の注目点

`qwen3.6:27b-mlx`を除外した代わりに検証対象へ追加したモデル。追加時点でOllama公式ライブラリページから確認できた事実と、それに基づく評価上の注目点をまとめる。

### 確認済み事実(Ollama公式ライブラリページより)

| 項目 | 値 |
|---|---|
| ダウンロードサイズ | 18GB(本体17GB + CLIPプロジェクタ931MB) |
| パラメータ数 | 27.3B(アクティブパラメータ数の記載が無いためdenseと推定) |
| 量子化 | Q4_K_M(GGUF/llama.cppネイティブ) |
| アーキテクチャ | `qwen35` |
| 機能タグ | vision / tools / thinking |
| ライセンス | Apache 2.0 |
| コンテキスト長 | ページに記載なし。実測が必要 |

モデル説明に明記されている特徴:

- **Core Capabilities**: コーディング・専門業務・リサーチ・長期的なエージェントタスク全般での改善
- **Agent Execution**: 自律的な計画立案の強化と、環境からのフィードバックのより適切な処理
- **Downstream Compatibility**: popular harnessesや開発ツールへの対応を拡大し、既存スタックへの統合を容易にした
- **Flexible Thinking Control**: thinkingモードはデフォルトでON。リクエスト単位で無効化可能。`reasoning_effort`で深さを調整可能。`preserve_thinking`で過去メッセージの推論文脈を保持
- **Vision-Language Understanding**: 画像・動画の理解に対応

### 差し替えの根拠

モデル説明の「Downstream Compatibility(ハーネス対応の拡大)」と「Agent Execution(環境フィードバックの処理)」は、ベンチマーク前の参考観測(下記セクション)で観測した`qwen3-coder:30b`の2つの失敗に正確に対応している。すなわち①`<function=Bash>`が平文で出力されツールが実行されなかった件がハーネス対応の問題、②`operation not permitted`を誤診しmacOSでLinuxの`systemctl`を提案した件が環境フィードバック処理の問題である。このため、**軸3・軸4でこれらの弱点に改善が見られるかが最大の注目点**となる。

### VRAM上の見込み

本体17GBは`gemma4:26b`のロード時SIZE(17GB)とほぼ同じ。`gemma4:26b`はコンテキスト長262144でも100% GPUを維持できたため(既知の結果)、`qwen3.8:27b`も131072は問題なく、262144も視野に入ると見込まれる(要実測、`bin/sweep.sh`で確定させる)。

### 速度上の懸念

27.3Bにアクティブパラメータ数の記載が無いためdenseと推定される。もし`qwen3-coder:30b`がMoE(30B-A3B等)であれば、1トークンあたりの実効計算量はdense 27.3Bの方が大きく、104.5 tok/sより遅くなる可能性が高い。`gemma4:26b`の86.1 tok/s前後かそれ以下が現実的な予想(要実測)。

### thinkingモードのリスク

thinkingモードがデフォルトでONであるため、思考トークンが生成時間とコンテキストを消費し、多ターンのエージェントループ(軸3・4)では体感速度が落ちる可能性がある。Claude Codeから第三者プロバイダに対して`thinking`パラメータを送る経路が無いため(`alwaysThinkingEnabled`は第三者プロバイダでは無効)、Claude Code側からthinkingを無効化できない可能性がある。回避策の候補として、thinkingを無効化したカスタムModelfile(`FROM qwen3.8:27b`をベースに派生モデルを作る)が考えられるが、正しいパラメータ名は未確認のため要検証。軸1・2のスイープ測定は`ollama run`で直接行うため、この問題の影響を受けにくく、影響が出るのは主に軸3・4である。`bin/sweep.sh`には`--think`オプションがあり、thinkingの有無を明示して測定できる。

### vision機能は本用途では不要

CLIPプロジェクタ931MBはPHPコード解析には使わないが、VRAMを消費する。実害は小さいが留意点として記載する。

## ベンチマーク前の参考観測(qwen3-coder:30b)

サンドボックス設定を検証する過程で、軸3・4に関わる挙動が2点観測された(設定の詳細は`README.md`を参照)。

1. `ollama ps`とだけ入力した1回目はツール呼び出しの形式が壊れ、`<function=Bash>`という平文がそのまま出力された(実行されず)。「上記のコマンドを実行してください」と明示した2回目は正常にツール呼び出しできたため、機構自体の故障ではなく、実行要求かどうかの判断に失敗したものと思われる。
2. ブロックされた後の原因診断が誤っていた。macOS環境にもかかわらずLinux用の`systemctl status ollama`を提案し、`operation not permitted`というサンドボックス特有のエラーを認識できず「Ollamaが起動していない」という誤った仮説を立てた(実際にはOllamaは正常稼働中)。

これらは軸3・軸4で測ろうとしている弱点が偶発的に観測された例であり、本番の採点時の参考にしてよい。

## 機密情報の分離ルールと根拠

実プロダクトのクラス名を含む具体的なタスク文面は、この仕様書に書かない。実プロダクトの機密情報にあたるため、実プロダクト用の環境内の別ファイルで保持すること。

**根拠**: この検証プロトコル(このファイルと手順書)自体は、複数モデル・複数回の検証で汎用的に使い回すことを想定した文書であり、Ollamaベンチマークを扱う一般セッション側でも参照される。一方、タスク1〜3の具体的な文面は対象コードの実クラス名・メソッド名を含み、これは実プロダクト環境内の機密情報にあたる。両者を同じファイルに混在させると、検証プロトコルを他プロジェクトや一般セッションで再利用・共有する際に機密情報が漏れる経路になる。そのため、実クラス名を含む具体的なタスク文面・正解セットは必ず実プロダクト環境内の別ファイルに分離して保持し、このファイル・手順書には型(パターン)としての説明のみを残す。
