# ベンチマークの使い方

## 目的

`gemma4:26b` / `qwen3-coder:30b` / `qwen3.8:27b` の3つのローカルLLMを Claude Code 上で
動かし、「コードベースを調査する能力」を比較評価するためのベンチマークです。

実際の機密プロダクトコードの代わりに、`fixture/` に合成PHPコードベース（クエスト報酬
システムを題材にした約90ファイル）を用意しています。評価軸は以下の2つです。

- **軸3: ツール呼び出し精度** — Read/Grep/Bash等を適切に選択できるか、構文エラーや
  存在しないパスの幻覚がないか（調査の**過程**を見る）
- **軸4: コード調査の精度** — 最終的な回答が正解セットと一致するか（**結論**を見る）

## ファイル構成

```
llm-bench/
├── fixture/            ベンチマーク対象のPHPコードベース（約90ファイル。`.claude/settings.json`と
│                       `CLAUDE.md`を同梱済み。正解情報は一切含まない）
├── bin/
│   ├── prepare.sh      モデルの切り替え・Ollamaサーバーの起動
│   ├── record.sh       回答のブラインド記録
│   ├── restore.sh      検証後のOllamaサーバー停止
│   └── sweep.sh        軸1・2の自動スイープ
├── tasks/tasks.md      AIエージェントに与えるタスク文面3件（コピペで使える）
├── answers/answers.md  正解セットと採点用の情報（デコイの説明・部分点の指針・rg再確認コマンド付き）
├── docs/setup.md       このファイル
└── results/            結果ファイル・回答・対応表の出力先
```

## 正解ファイルをリポジトリ外に置いている理由

`answers/answers.md` と `tasks/tasks.md` を `fixture/` の外に置いているのは、
評価対象のエージェントが `fixture/` を検索して正解や「これがベンチマークである」ことに
気づいてしまうと、評価そのものが無意味になるためです。`fixture/` の中には
README・コメント・ファイル名のいずれにも "benchmark" 等の語や正解のヒントを含めていません。
また `fixture/CLAUDE.md` にはコーディング規約等の一般的なルールのみを記載しており、
`AGENTS.md` や `.claude/rules/` のようなプロジェクト固有の探索誘導は置いていません。

## 使い方の手順

1. `bin/prepare.sh` でモデルを切り替え、Ollamaサーバーを起動します。

   ```bash
   ./bin/prepare.sh <model名>
   # 例: ./bin/prepare.sh qwen3-coder:30b
   ```

   設定テーブルに登録済みのモデル（`gemma4:26b` / `qwen3-coder:30b` / `qwen3.8:27b`）は
   コンテキスト長を自動解決します。`fixture/.claude/settings.json` は既にこのリポジトリに
   同梱されているため、本番環境の設定に合わせて別途用意する必要はありません。
   `prepare.sh` は同ファイルの `model` / `env.CLAUDE_CODE_MAX_CONTEXT_TOKENS` /
   `env.CLAUDE_CODE_AUTO_COMPACT_WINDOW` の3キーだけを書き換え、`permissions` や `sandbox`
   等モデル間で揃えるべき他の設定はそのまま維持します。3モデルの比較が成立するのは、
   この3キー以外の条件が常に同一に保たれているためです。

2. Claude Code を起動します。

   ```bash
   cd fixture && claude --setting-sources project
   ```

3. タスクを1件ずつ実施します。`tasks/tasks.md`（`fixture/` の外、リポジトリ直下のファイル）に
   記載の3つのタスク文面を、そのままコピペして投げてください。

   - **各タスクの前に必ず `/clear` を実行し、会話履歴をリセットしてください。**
     前のタスクの調査過程や回答が残っていると、後続タスクの難易度・公平性が変わります。
   - 1タスクごとに、エージェントの最終回答と、ツール呼び出しの過程（Read/Grep/Bashの
     選択、存在しないパスへのアクセス試行がないか等）の両方を記録してください。

4. エージェントの回答を `./bin/record.sh <task-number>` でブラインド記録します。

   ```bash
   ./bin/record.sh 1
   ```

   `record.sh` は現在のモデル名を `fixture/.claude/settings.json` から自動で読み取り、
   `results/answers/` にまだ存在しない `answer-01`〜`answer-99` の中からランダムに
   ブラインドIDを選び、`results/mapping.tsv` にモデル名との対応行を追記したうえで、
   タスク番号だけを書いた空の回答ファイル `results/answers/<blind-id>.md` を作成します。
   このファイルにエージェントの回答を貼り付けて保存してください。

5. 3タスク終了後、`answers/answers.md`（`fixture/` の外、リポジトリ直下のファイル）を参照して
   採点します。各タスクに、正解セット・デコイの説明・部分点の与え方の指針・`rg` による
   再確認コマンドを記載しています。

6. 検証が終わったら `./bin/restore.sh` でベンチマーク用に起動した Ollama サーバーを
   停止してください。

   ```bash
   ./bin/restore.sh
   ```

## 実プロダクトと条件が異なる点（正直な申告）

以下の点で、このベンチマーク環境は実際のプロダクト環境と異なります。比較結果を
解釈する際に留意してください。

- **`AGENTS.md` や `.claude/rules/` が無い**: 実プロダクト側にプロジェクト固有の
  ルールファイルがある場合、それによってエージェントの探索戦略が誘導されている
  可能性があります。本ベンチマークにはそうした誘導が一切ないため、より「素の」
  調査能力に近い形で評価されます。
- **リポジトリ規模が異なる**: 実プロダクトはこの合成リポジトリ（約90ファイル）より
  大幅に大きい可能性があります。コンテキスト長・検索効率の差は、リポジトリ規模に
  応じて本番よりも大きく・小さく出ることがあります。
- **実際のコードの癖が異なる**: 合成コードはレイヤードアーキテクチャに忠実で、
  命名やスタイルも一貫させています。実プロダクトにある歴史的経緯による不規則な
  命名・密結合・巨大クラスなどは再現していません。そのため、実プロダクトでの
  調査難易度を過小評価する可能性があります。
- **実行環境が無い**: `composer install` や PHPUnit の実行を前提としていません
  （タスク3のテスト失敗出力はタスク文面に直接記載しており、実行は不要です）。
  実行結果を確認しながら調査するタイプのタスクは含まれていません。

## 注意事項

- `fixture/` はベンチマーク中に上書きしても構いません（正解セットは外部の
  `answers/answers.md` にあるため、リポジトリ自体を汚しても評価には影響しません）。
- 3モデルの比較を行う際は、`fixture/` を毎回まっさらな状態からコピーし直して
  ください。一度のセッションでエージェントが `fixture/` にファイルを書き込んだ
  場合、次のモデルの評価に影響する可能性があります。
