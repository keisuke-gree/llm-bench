# ローカルLLMモデル性能検証 手順書

このファイルは**実行用の手順書(ランブック)**です。ターミナルでコマンドをコピペしながら、上から順に実行してください。このファイル単独で作業を完了できるように作ってあります。

対象モデル: `gemma4:26b` / `qwen3-coder:30b` / `qwen3.8:27b`

検証する4つの軸の定義、タスク1〜3の型、軸3・軸4の採点基準など「何を・なぜ測るか」は、**仕様書`spec.md`** にまとめてあります。実行中に定義や採点基準を確認したくなった場合はそちらを参照してください(このファイルにも要所には仕様書への参照を残しています)。

検証中は`fixture/.claude/settings.json`の書き換えが何度も発生するため、**必ずフェーズAの手順1から始め、モデルを切り替えるたびに手順10で自動化スクリプトを使うこと**。検証が完了したら、フェーズE(手順23〜25)でベンチマーク用に起動した`ollama serve`を停止すること。
`fixture/.claude/settings.json`の書き換えと`ollama serve`の起動は、手順2で配置する自動化スクリプト(`bin/prepare.sh`)1回の実行にまとめられている。

本体は「手順1」から始まる通し番号のランブックになっている。各手順には実行者(**人間** / **エージェント**)
を明記してあるので、上から順に辿ればよい。

## 自動実行(推奨): `benchmark-run` Skill

以下の手順1〜25は、各ステップを個別に手動実行したい場合の詳細な参照用です。通常は
これを1手順ずつ辿る必要はなく、**リポジトリのルートディレクトリ**でClaude Codeを
起動し、`benchmark-run` Skillを呼び出せば、フェーズA〜Eの大部分(軸1・2の測定、
正解セットの退避・復元、モデルごとの軸3・4のタスク実行、採点、レポート生成、片付け)
が自動で通しで実行されます。

```bash
ollama pull <model名>   # 未取得のモデルがあれば(人間が実行)
claude                  # リポジトリのルートディレクトリで起動
# セッション内で「benchmark-run Skillでベンチマークを実行して」等と依頼する
```

人間がやることは、対象モデルを`ollama pull`で取得しておくことと、ルートディレクトリで
Skillを呼ぶことの2つだけになる。Skillが自動化する内容の詳細は
`.claude/skills/benchmark-run/SKILL.md`を参照(手順書との対応関係は各フェーズの
冒頭に記載する)。

以下の手動手順は、Skillが使えない場合や、1ステップずつ確認しながら進めたい場合の
フォールバックとして残す。

## 役割分担

`benchmark-run` Skillを使う場合、下表の「エージェント」の作業はすべて自動で実行されます。

| 作業 | 実行者 |
|---|---|
| `ollama pull`によるモデルの取得 | **人間**(ネットワークアクセスを伴う。エージェントは実行せず、未取得なら停止して人間に伝える) |
| `bin/sweep.sh`・`bin/prepare.sh`・`bin/run-tasks.sh`・`bin/restore.sh`の実行 | **エージェント**(リポジトリのルートで起動したセッションから。ただし`auto mode`が必要。下記参照) |
| 軸3・4のタスク実施と回答・トレースの保存 | **エージェント**(`bin/run-tasks.sh`が`claude -p`で無人実行する) |
| 軸4の採点(正解セットとの突き合わせ) | **エージェント**(`benchmark-score` Skill。集合の比較は機械的なため信頼できる) |
| 軸3の採点(トレースからのツール呼び出しの評価) | **エージェント**(`benchmark-score` Skill。`results/traces/`のイベントストリームを読む) |
| レポートの生成と考察 | **エージェント**(`benchmark-report` Skill) |
| 結果の妥当性の確認 | **人間**(スコアと考察が実測値と整合しているかを最後に確認する) |

### `auto mode` の指定方法

```bash
claude --permission-mode auto
```

起動後に切り替える場合は、セッション内で`Shift+Tab`を押すとモードが順に切り替わり、`auto`を選べます。

**`.claude/settings.json`の`permissions.defaultMode`では指定できません。** `auto`はプロジェクトスコープの設定では付与できず、無視された上でユーザー設定のモードを覆い隠します。そのため設定ファイルには書かず、起動時に毎回指定します。

### `auto mode` が必要な理由

`bin/`配下のスクリプトは`ollama serve`でポートをbind(listen)します。**サンドボックスはbindを拒否するため**(`Error: listen tcp 127.0.0.1:11434: bind: operation not permitted`)、サンドボックス外での実行が必要になります。

`sandbox.network.allowedDomains`で`127.0.0.1:11434`を許可しても解決しません。**あの設定は外向きの接続にのみ適用され、bindには効かない**ことを実測で確認しています。

加えて、エージェントが組み立てるコマンドにはパイプやリダイレクトを含む複合コマンドが現れます。`permissions.allow`に個々のスクリプトを登録しても、複合コマンドは確認を求められることがあり、**事前に列挙し尽くすことは原理的に不可能**です。

したがって`auto mode`での運用を前提とします。`llm-bench`は機密情報を含まず、`permissions.deny`で`sudo`・`rm`・`git push`は塞いであります。

**測定される側(`fixture/`)は別です。** あちらは`sandbox.enabled: true`かつ`allowUnsandboxedCommands: false`のままで、サンドボックスを外す経路がありません。外部通信も`ollama`の実行もできません。この隔離は維持されています。

## モデルごとの設定値

手順の中で何度も参照する値なので、先にここにまとめておく。各モデルにこの値を与える設計判断(なぜモデルごとに異なる値なのか)は仕様書`spec.md`の「モデルごとの設定値: 値の決め方の方針」を参照。

| モデル | `OLLAMA_CONTEXT_LENGTH` | `CLAUDE_CODE_MAX_CONTEXT_TOKENS` | `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | 根拠 |
|---|---|---|---|---|
| `qwen3-coder:30b` | `131072` | `131072` | `115000` | 2026-08-12実測(100% GPU / SIZE 25GB / 104.5 tok/s)。262144では12%がCPUに溢れ34.3 tok/sに低下するため131072が上限。`bin/prepare.sh`の設定テーブルに登録済みで自動解決される |
| `gemma4:26b` | `262144` | `262144` | `230000` | 2026-08-12実測(100% GPU / SIZE 17GB)。`ollama show`のアーキテクチャ上限も262144のため、これが最大値。`bin/prepare.sh`の設定テーブルに登録済みで自動解決される |
| `qwen3.8:27b` | `131072`(`bin/prepare.sh`の設定テーブルに登録済みで自動解決される) | 同左と同じ値 | 上記に0.877を掛けた値 | 未測定のため(Ollama公式ライブラリページにもコンテキスト長の記載が無い)、暫定的に`qwen3-coder:30b`と同じ`131072`を登録した値。フェーズB(手順8)の実測で100% GPUを維持できず、より小さい値が実用上限だと判明した場合は`--context-length`で明示的に上書きすること |

- **3つの値は必ずセットで揃えること。** 揃っていないとauto-compactの発火タイミングがずれ、モデル間の比較が成立しなくなる(`bin/prepare.sh`導入後はこの3つが1回の実行で自動的に揃うため、揃え忘れのリスクは解消されている。`CLAUDE_CODE_AUTO_COMPACT_WINDOW`の算出方法は手順10を参照)

```json
"model": "qwen3-coder:30b",

  "CLAUDE_CODE_MAX_CONTEXT_TOKENS": "131072",
  "CLAUDE_CODE_AUTO_COMPACT_WINDOW": "115000"
```

> **注意**: 上記は`model`/`env`の該当部分のみを抜き出した差分です。ファイル全体をこの内容で置き換えないこと。`permissions`(allow/deny)や`sandbox`等の他の設定は必ずそのまま残してください(これらを失うと外部通信の制限が丸ごと外れます)。`bin/prepare.sh`自身も`model`/`env`の2キー/`sandbox.filesystem.denyRead`のみをパッチするため、他の設定を書き換えることはない。

このリポジトリはベンチマーク専用に`fixture/`として用意されたものであり、実プロダクト環境そのものではない。そのため、ここで確認する値は「検証開始時点の初期値」であって「検証完了後に戻すべき本番値」ではない点に注意する(`bin/restore.sh`はこの値を復元しない設計になっている。詳細はフェーズE参照)。`model` / `CLAUDE_CODE_MAX_CONTEXT_TOKENS` / `CLAUDE_CODE_AUTO_COMPACT_WINDOW`の3つは常にセットで揃える必要があり、検証中はモデルを切り替えるたびに手順10の`bin/prepare.sh`がこの3つをまとめて書き換える。

### 手順2(人間)自動化スクリプトが動作することを確認する

`bin/`配下に`prepare.sh` / `record.sh` / `restore.sh` / `sweep.sh`の4本が既に用意されている。実行権限とヘルプ表示を確認しておく。

- `prepare.sh`: **フェーズC(軸3・4の実行)**で使う。モデルの切り替え・`fixture/.claude/settings.json`の書き換え・`ollama serve`の起動までを1回の実行で行う。
- `record.sh`: **フェーズC**で使う。回答のブラインドID採番と対応表への記録、空の回答ファイル作成を行う。
- `restore.sh`: **フェーズE(復元)**で使う。`prepare.sh`が起動した`ollama serve`を停止する(それ以外の復元は行わない)。
- `sweep.sh`: **フェーズB(軸1・2の自動スイープ)**で使う。コンテキスト長は`OLLAMA_CONTEXT_LENGTH=N ollama serve`という形でプロセス起動時の環境変数として渡すだけで、設定ファイルは一切書き換えない。

**フェーズBでは`prepare.sh`を使わない**。両スクリプトは書き換え対象も書き換え方式も異なるため、`prepare.sh`の役割は「フェーズCでのモデル切り替え」に限定される。

```bash
# このリポジトリのルートディレクトリで
chmod +x bin/prepare.sh bin/record.sh bin/restore.sh bin/sweep.sh
./bin/prepare.sh --help
./bin/record.sh --help
./bin/restore.sh --help
./bin/sweep.sh --help
```

4つすべてのヘルプが正しく表示されることを確認する。

> **注意**: いずれのスクリプトも**人間が通常のターミナルから**実行すること。Claude Codeのエージェント経由では、サンドボックスのlocalhost遮断・書き込み制限により正しく動作しない(役割分担セクションで検証済みの制約と同種の理由)。

### 手順3(人間)3モデルがpull済みか確認する

`ollama list`を実行し、`gemma4:26b` / `qwen3-coder:30b` / `qwen3.8:27b`の3モデルが揃っているか確認する。無いものがあれば`ollama pull <model名>`で取得する(公式レジストリからの取得は自社ルールで認められた運用)。

> **注記**: `qwen3.8:27b`は未取得の場合、`ollama pull qwen3.8:27b`が必要になる可能性が高い(ダウンロードサイズ18GB程度)。

> **`qwen3.8:27b`固有の注意(thinkingモード)**: `qwen3.8:27b`はthinkingモードがデフォルトでONのため、思考トークンの生成が生成時間とコンテキストを消費し、多ターンのエージェントループ(フェーズCの軸3・4)では体感速度が落ちる可能性がある。Claude Codeから第三者プロバイダに対して`thinking`パラメータを送る経路が無く(`alwaysThinkingEnabled`は第三者プロバイダでは無効)、Claude Code側からthinkingを無効化できない可能性がある。回避策の候補として、thinkingを無効化したカスタムModelfile(`FROM qwen3.8:27b`をベースに派生モデルを作る)が考えられるが、正しいパラメータ名は未確認のため要検証。**軸1・2のスイープ測定(フェーズB)は`ollama run`を直接使うため、この問題の影響を受けにくい。**影響が出るのは主に軸3・4(フェーズC)である。詳細は仕様書`spec.md`の「`qwen3.8:27b`を追加した理由と評価上の注目点」を参照。

### 手順6(人間)`OLLAMA_KEEP_ALIVE`の延長方針を確認する

軸3・4のタスクは人間の確認待ちや多段階のツール呼び出しでアイドルが発生しやすく、アイドル5分でモデルが自動アンロードされると、生成が遅いモデルほど再ロードの分だけ不当に不利になり、モデル間の比較が公平でなくなる。

`bin/prepare.sh`は`OLLAMA_KEEP_ALIVE`を`ollama serve`プロセスの環境変数として渡す(既定値`30m`。手順10で使用)。`~/.zshrc`のような永続ファイルには一切書き込まないため、「戻し忘れ」という概念自体が存在しない。フェーズE(手順23)で`bin/restore.sh`がそのサーバープロセスを止めれば、延長した`OLLAMA_KEEP_ALIVE`もプロセスごと消える。

なお、フェーズB(軸1・2の自動スイープ)は`bin/sweep.sh`が測定ごとに明示的にモデルをロード・アンロードするため、アイドルタイムアウトの影響を受けず、`OLLAMA_KEEP_ALIVE`の値とは無関係に動作する。ここでは、この運用方針を確認するだけでよい。

## フェーズB: 軸1・軸2の測定(すべて人間、Claude Code不要)

3モデル×4段階のコンテキスト長(`32768`/`65536`/`131072`/`262144`、全12組)の測定を、`bin/sweep.sh`1コマンドの実行に置き換える。手動でやる場合はコンテキスト長を切り替え、`ollama serve`を再起動し、`ollama ps`と`ollama run --verbose`を手動で実行し、結果を手でテーブルに記入する、という12回程度の反復が必要になるが、この一連の流れをスクリプトが内部で自動化する。

このフェーズはClaude Codeセッションを起動せず、人間が普通のターミナルで完結させる(エージェント経由ではサンドボックスのlocalhost遮断により`ollama`コマンドが使えず動作しないため)。

### 手順7(人間)手動起動している`ollama serve`を停止する

`sweep.sh`は既存の`ollama serve`が動いている場合エラーで停止する(`--force`で強制停止して続行することも可能)。まずは別ターミナルで動かしている`ollama serve`をCtrl+Cで停止しておく。

### 手順8(人間)`sweep.sh`を実行する

```bash
./bin/sweep.sh
```

デフォルトでは3モデル×4段階のコンテキスト長、全12組を測定する。対象を絞りたい場合は`--models`/`--contexts`で指定できる(再測定や追加測定用):

```bash
# 例: qwen3.8:27bだけ、131072と262144だけ再測定する
./bin/sweep.sh --models "qwen3.8:27b" --contexts "131072,262144"
```

その他のオプション:

| オプション | 用途 |
|---|---|
| `--runs N` | 1組あたりの測定回数(既定4回。1回目は`load duration`が大きいため常に破棄し、残りの平均を取る) |
| `--output PATH` | 結果ファイルの出力先を指定する |
| `--force` | 既存の`ollama serve`を強制停止して続行する |
| `--dry-run` | 何を何組測定するかの計画だけ表示し、実際の測定は行わない |
| `--help` | 使い方を表示する |

**所要時間の目安**: 12組×(モデルロード+4回生成)で、おおよそ10〜20分程度と見込まれる(モデルサイズや生成量により変動する)。

**スクリプトの重要な特徴**:
- **`~/.zshrc`も`.claude/settings.json`も一切書き換えない**。コンテキスト長は`OLLAMA_CONTEXT_LENGTH=N ollama serve`という形で環境変数をプロセス起動時に渡すため、設定ファイルの書き換え事故のリスクがゼロ
- Ollamaサーバーのライフサイクルをスクリプト自身が管理する(コンテキスト長ごとに起動・停止)
- 各モデルの測定後に明示的に`ollama stop`を実行し、前のモデルがVRAMに残って次の測定を汚染することを防ぐ
- 終了時(Ctrl+C含む)に自分が起動したサーバーを確実に停止する

1組ごとの内部処理: モデルをロード → `ollama ps`で`SIZE`/`PROCESSOR`/`CONTEXT`を記録 → 固定プロンプト(手順4で決めたもの)で4回生成し1回目を除く3回の`eval rate`を平均 → `ollama stop`でアンロード。

### 手順9(人間)結果ファイルを確認し、各モデルの実用上限値を把握する

生成された結果ファイルには以下が含まれる:
- 軸2用のマトリクス表(モデル×コンテキスト長)
- モデルごとの実用上限値サマリ
- 各組のSIZE一覧(オーケストレーション構成の検討材料)

`PROCESSOR`列・`eval rate`欄の詳しい読み方は付録2「`ollama ps`/`eval rate`の読み方」を参照。**このフェーズが終わると、各モデルの「実用上限値」(100% GPUを維持できる最大値)が確定する。** 確定した値は「モデルごとの設定値」テーブルとフェーズCで使用する。過去の実測値(参考値)は仕様書`spec.md`の「軸1: 生成速度 — 既知の結果」を参照。

## フェーズC: 軸3・4の実行フェーズ(人間とエージェントが分担、モデルごとに繰り返す)

軸1・2で確定した各モデルの実用上限値を使う(溢れた状態でやると、モデルの実力差ではなくCPU溢れの遅さが混ざるため)。

このフェーズでは、モデルごとにタスク1〜3を実行し、回答を保存するところまでを行う。**採点はこのフェーズでは行わない**(全モデルの実行が終わってからフェーズDでまとめて実施する。理由はフェーズDの冒頭を参照)。

> **自動実行の場合**: このフェーズの「正解セットの退避」「タスクの実行」「回答の保存」は
> `bin/hide-answers.sh --hide`と`bin/run-tasks.sh`で自動化されている(`benchmark-run` Skillが
> 内部で呼び出す)。`bin/run-tasks.sh`は`bin/record.sh`によるブラインドID払い出しから
> `claude -p --output-format stream-json --verbose`での無人実行、回答ファイルへの保存までを
> 1コマンドで行い、`answers/`が`bin/hide-answers.sh`で退避されていなければ安全装置として
> エラーで停止する。手順10〜15は手動実行時の参照用の詳細である。
>
> **軸3の採点にはトレースファイルが必須である。** `bin/run-tasks.sh`は最終回答テキストを
> `results/answers/<ブラインドID>.md`へ、ツール呼び出しを含む全イベントストリームを
> `results/traces/<ブラインドID>.jsonl`へ、それぞれ保存する。軸3(調査の過程)の採点は
> 後者を読んで行う(詳細は`.claude/skills/benchmark-score/SKILL.md`を参照)。トレース
> ファイルが存在しない回答は、軸3を「測定不能」として扱いスコアを付けない
> (フェーズDの手順20・21を参照)。

### 手順10(人間)`bin/prepare.sh`でモデルを切り替え、`ollama serve`を起動する

設定テーブル登録済みのモデル(`qwen3-coder:30b` / `gemma4:26b` / `qwen3.8:27b`)は、コンテキスト長がテーブルから自動解決されるので`--context-length`は不要:

```bash
./bin/prepare.sh <model名> --keep-alive 30m
# 例: ./bin/prepare.sh gemma4:26b --keep-alive 30m
```

テーブルに登録されていない新しいモデルを追加した場合は、軸2で確認した実用上限値を`--context-length`で明示する:

```bash
./bin/prepare.sh <未登録モデル名> --context-length <軸2で確認した実用上限値> --keep-alive 30m
```

`bin/prepare.sh`は`CLAUDE_CODE_AUTO_COMPACT_WINDOW`を、指定したコンテキスト長に本番と同じ比率(`115000 / 131072 ≈ 0.877`)を掛けて自動算出する(1000単位に丸め)。例: 実用上限値が`65536`なら`65536 × 0.877 ≈ 57000`程度になる。値は「モデルごとの設定値」テーブルも参照すること。

`model`に渡す名前は`ollama run`で使うタグ名(`gemma4:26b`等)をそのまま使う。

> **注意**: `fixture/.claude/settings.json`の書き換えは、スクリプトが`jq`で`model`/`CLAUDE_CODE_MAX_CONTEXT_TOKENS`/`CLAUDE_CODE_AUTO_COMPACT_WINDOW`/`sandbox.filesystem.denyRead`の4キーのみをパッチし、書き換え前に`fixture/.claude/settings.json.bak.<timestamp>`へバックアップを作成したうえで、書き換え後に`permissions`(allow/deny)や`sandbox`の他設定が失われていないか・`model`が正しく反映されているか・`denyRead`に`answers/`が含まれているかを検証する。`denyRead`はリポジトリの配置場所が値に入るため、実際の配置場所から毎回組み立て直す(`~/llm-bench`以外にcloneしても手直し不要)。問題があればバックアップから復元して中断するため、手動編集時代に最も注意が必要だった「他設定を丸ごと失う事故」は起きない。また、指定したモデルが`ollama list`に無い場合はタイプミスとしてエラーで停止する(`ollama`コマンド自体が使えない環境では警告のみで続行する)。

### 手順11(人間)既存の`ollama serve`の扱いを理解する

`bin/prepare.sh`は、既に動いている`ollama serve`を**`--force`を付けた場合のみ**停止してから続行する。付けない場合は、人間が手動で起動した別の用途のサーバーを誤って落とさないよう、エラーで停止して確認を促す。

```bash
./bin/prepare.sh gemma4:26b --keep-alive 30m --force
```

`--force`で既存サーバーを停止したあと、`bin/prepare.sh`は`OLLAMA_CONTEXT_LENGTH`と`OLLAMA_KEEP_ALIVE`をプロセスの環境変数として渡した新しい`ollama serve`をバックグラウンドで自動的に起動する。以前のように人間が別ターミナルで`Ctrl+C`→`source ~/.zshrc`→`ollama serve`を手動で行う必要はない。

この再起動により、起動中のClaude Codeセッションがあれば推論バックエンドへの接続を失う。セッションは手順13で新規に起動し直すこと(再起動前に開いていたセッションは終了してよい)。

### 手順12(人間)起動確認の内容を理解しておく

`bin/prepare.sh`は、サーバーに接続できるようになるまで待ち、ウォームアップ生成を1回実行したうえで`ollama ps`を確認し、`PROCESSOR`が厳密に`100% GPU`でなければ大きな警告を表示する(CPUへの溢れがあると速度が不安定になり、モデル間の比較が成立しなくなるため)。警告が出た場合は`--context-length`を下げて`bin/prepare.sh`を実行し直すこと。人間が個別に`ollama ps`や`ollama run --verbose`を手動実行する必要は基本的にない。

追加で手動確認したい場合は、手順4の固定プロンプトで`ollama run --verbose`を実行し、速度がフェーズBの結果ファイル(手順9)に記録した値と一致することを確認するとよい。**ただしエージェントにはこれを実行させられない**(サンドボックスのlocalhost遮断、役割分担セクションで検証済み)ため、必要であれば人間が別ターミナルで行い、結果はエージェントの記録用に共有してよい。

### 手順14(エージェント)タスク1〜3を実施し、回答を保存する

各タスクの実行前に必ず`/clear`する(前タスクの情報がコンテキストに残っていると精度評価が歪む)。手順5で用意した文面を投入し、エージェントの回答を得たら`bin/record.sh`で保存する。

```bash
./bin/record.sh <task番号>
# 例: ./bin/record.sh 1
```

`record.sh`は`fixture/.claude/settings.json`から現在のモデル名を`jq`で読み取り(人間がモデル名を手入力することはない)、`results/answers/`配下にまだ存在しない`answer-01`〜`answer-99`の中からランダムにブラインドIDを選び(通し番号ではなくランダムにするのは、採番順からどのモデルを先に試したか推測されないようにするため)、`results/mapping.tsv`にモデル名・コンテキスト長・タスク番号・記録日時の対応行を追記したうえで、タスク番号だけを書いた空の回答ファイル`results/answers/<blind-id>.md`を作成する。エージェントの回答をこのファイルに貼り付けて保存すること。

各タスクは原則1回のみ実施する(一発勝負の評価)。スコアが僅差で判断に迷う場合のみ同一タスクを2回実施し平均を取る、というルールの詳細は仕様書`spec.md`の軸3・軸4の「実行回数について」を参照。

### 手順15(人間)トランスクリプトパスの控え

どのファイルがどのモデルの何番のタスクかの対応表は、手順14の`bin/record.sh`が`results/mapping.tsv`に自動記録済みである。**このファイルは採点フェーズ(フェーズD)では絶対に参照しないこと**(ブラインド採点のため)。あわせて、そのセッションのトランスクリプト(`~/.claude/projects/<project>/<session-id>.jsonl`)のパスを控えておく(軸3の採点でツール呼び出しログを参照するため)。

**自動実行(`bin/run-tasks.sh`)の場合は、この手順は不要である。** ツール呼び出しを
含む全イベントストリームが`results/traces/<ブラインドID>.jsonl`として自動保存されて
いるため、手動でトランスクリプトパスを控える必要はない。

## 付録1: `bin/prepare.sh`が使えない場合の手動フォールバック

通常は手順10で`bin/prepare.sh`を使う。スクリプトが未配置・実行権限エラー等で使えない場合のみ、以下の手動手順を代わりに使う。

### `fixture/.claude/settings.json`の手動書き換え

```json
{
  "model": "<model名>",
  "env": {
    "CLAUDE_CODE_MAX_CONTEXT_TOKENS": "<コンテキスト長と同じ数値>",
    "CLAUDE_CODE_AUTO_COMPACT_WINDOW": "<コンテキスト長に0.877を掛けて1000単位に丸めた値>"
  }
}
```

> **注意**: 上記は`model`/`env`の該当部分のみを抜き出した差分です。**ファイル全体をこの内容で置き換えないこと。** `permissions`(allow/deny)や`sandbox`等の他の設定は必ずそのまま残してください(これらを失うと外部通信の制限が丸ごと外れます)。手動編集ではこの事故が最大のリスクなので、テキストエディタで該当キーの値のみを差し替える形で編集すること。

書き換え後は、`OLLAMA_CONTEXT_LENGTH=<コンテキスト長> OLLAMA_KEEP_ALIVE=30m ollama serve`のように環境変数を明示して`ollama serve`を起動し直す(`bin/prepare.sh`と同様、`~/.zshrc`は書き換えない)。

## 付録2: `ollama ps`/`eval rate`の読み方(結果ファイルの解釈に使う背景知識)

`sweep.sh`が自動生成する結果ファイルを読み解くために、以下の背景知識を持っておくと役立つ。また、スクリプトが使えない場合に手動で測定する際もこの知識を使う。

### `ollama ps`の出力例

```
NAME              SIZE     PROCESSOR    CONTEXT   UNTIL
qwen3-coder:30b   25 GB    100% GPU     131072    4 minutes from now
```

- `PROCESSOR`が`100% GPU`なら合格(そのコンテキスト長はVRAM予算内)
- `xx% CPU / yy% GPU`と出たら溢れている。溢れた場合も速度は記録され、「溢れた場合にどれだけ遅くなるか」のデータとして扱う

### `ollama run --verbose`の出力例

2026-08-25、`qwen3-coder:30b`で動作確認済み:

```
total duration:       8.056091333s
load duration:        7.720224625s
prompt eval count:    9 token(s)
prompt eval duration: 42.446ms
prompt eval rate:     212.03 tokens/s
eval count:           29 token(s)
eval duration:        280.437ms
eval rate:            103.41 tokens/s   ← これを記録する
```

`eval rate`欄がそのままtokens/secになる(curl/jq不要)。同じ固定プロンプトで複数回実行し、初回(モデルロード直後で`load duration`が大きい)を除いた平均を取る、という考え方は`sweep.sh`の`--runs`オプションにもそのまま引き継がれている。

### 手動で1組だけ再測定する場合

`sweep.sh`が使えない場合や、個別に1組だけ手動確認したい場合は、次のように直接測定できる:

```bash
ollama run <model名> "warmup"
ollama ps
ollama run <model名> "<手順4で決めた固定プロンプト>" --verbose
```

## 実施メモ

- 軸3・4の`/clear`によるコンテキストリセットについては手順14を参照
- `OLLAMA_KEEP_ALIVE`の延長(既定`30m`)とその理由については手順6・手順10を参照。`bin/prepare.sh`が`ollama serve`起動時の環境変数として渡すだけなので`~/.zshrc`のような永続ファイルへの書き込みは発生せず、フェーズE(手順23)で`bin/restore.sh`によりそのプロセスごと停止すれば延長分も消える(フェーズBは`bin/sweep.sh`が測定ごとに明示的にモデルをロード・アンロードするため、そもそもアイドルタイムアウトの影響を受けない)
- 軸3・4の具体的なタスク文面(実クラス名を含むもの)をこのファイルに書き足さない件については手順5を参照(根拠は仕様書`spec.md`の「機密情報の分離ルールと根拠」を参照)
- 回答ファイルとモデル名の対応表(`results/mapping.tsv`)は手順14の`bin/record.sh`が自動的に記録する。採点フェーズ(フェーズD)では絶対に参照しないこと(ブラインド採点のため)。手順15参照
- モデル切り替えのたびに「`fixture/.claude/settings.json`の`model`」「同`CLAUDE_CODE_MAX_CONTEXT_TOKENS`/`CLAUDE_CODE_AUTO_COMPACT_WINDOW`」の3箇所を揃え忘れないこと(揃っていないとauto-compactのタイミングがずれ、正しい比較にならない。手順1・手順10参照。`bin/prepare.sh`導入後は手順10の1回の実行でこの3箇所が自動的に揃う)
- 全軸の結果が揃ったら、このファイルの記入欄を埋めた上で一般セッション側にスコアのみ報告してもらえれば、モデル選定の見直し要否を一緒に判断できる
- 検証完了後は必ずフェーズE(手順23〜25)の手順で`bin/restore.sh`を実行し、ベンチマーク用に起動した`ollama serve`を停止すること(`fixture/.claude/settings.json`は自動では戻らない。通常のOllama運用に戻す手順は手順24を参照)
