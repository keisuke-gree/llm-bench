ローカルLLMモデル選定レポート

対象: gemma4:26b / qwen3-coder:30b / qwen3.8:27b
測定日: 2026-08-26 〜 2026-08-27 ／ 環境: Apple M5 Max (VRAM実測 28.1 GiB) + Ollama + Claude Code

結論

本番モデルを gemma4:26b に変更することを推奨する。

最高精度（軸4: 14/15）と最高の調査過程品質（軸3: 15/15）を、実用的な速度で達成した唯一のモデル。 3タスク合計の所要時間は現行の qwen3-coder:30b の 1.39倍にとどまり、 最も難しいタスク2では逆に高速だった（1分35秒 対 1分54秒）。 加えてコンテキスト長が2倍（262144）、VRAM消費が8GB少ない（17GB）。

qwen3.8:27b は精度で gemma4:26b と完全に同点だが、所要時間が 10.2倍（48分14秒 対 4分43秒）であり、厳密に劣位。

用語集（クリックで展開）
eval rate
モデルが出力を生成する速度（1秒あたりのトークン数）。eval count ÷ eval duration で求まる。入力を読む速度とは別物で、体感速度を支配するのはこちら。
eval count
モデルが生成した出力のトークン数。実際の待ち時間は eval count ÷ eval rate で決まるため、速度だけ見ても待ち時間は分からない。
prompt eval rate
入力（プロンプト）を読み込む速度。全トークンを並列に処理できるため eval rate より速い。
トークン
モデルが文章を扱う最小単位。日本語なら1〜2文字、英語なら単語の一部程度に相当する。
tok/s
tokens per second。1秒あたりに生成できるトークン数。
コンテキスト長
モデルが一度に扱える入力と出力の合計トークン数の上限。これを超えると古い内容が失われる。
KVキャッシュ
生成の途中結果を保持するメモリ領域。コンテキストが長いほど大きくなり、VRAMを消費する。
VRAM
GPUが使えるメモリ。Apple Siliconでは本体メモリと共有され、この環境では実測28.1 GiBが上限。
PROCESSOR
ollama ps が表示する列で、モデルがGPUとCPUのどちらで動いているかの比率。100% GPU が理想的な状態。
SIZE
ollama ps が表示する列で、そのモデルがメモリ上で占める大きさ。モデルの重みとKVキャッシュの合計。
CPU溢れ
モデルがVRAMに収まらず一部がCPU側で処理されること。オフロードとも呼び、速度が激減する。
MoE
Mixture-of-Experts。モデル内部を複数の「専門家」に分け、1トークンごとに一部だけを使う構造。総パラメータが大きくても計算量が少なく高速。
dense
MoEと対になる構造で、1トークンごとに全パラメータを使う。同じサイズならMoEより遅くなる。
メモリ帯域
メモリからデータを読み出せる速さ（GB/s）。denseモデルの速度上限を決める物理的な制約。
量子化
モデルの重みを低い精度に圧縮してサイズを小さくする技術。Q4_K_M は約4bitに圧縮する代表的な方式。
thinkingモード
回答の前に思考過程を生成するモデルの動作。精度が上がることがあるが生成トークンが増えて時間がかかる。
auto-compact
会話がコンテキスト長の上限に近づいた際、Claude Codeが自動で要約して圧縮する機能。
型エラー
TypeError。宣言された型と異なる型の値を渡したときにPHPが発生させるエラー。
strict_types
PHPの厳格な型チェックモード。有効にすると型の自動変換を行わずエラーにする。
文字列補間
"文字列{$変数}" のように文字列の中に変数を埋め込む書き方。どんな型でも文字列に変換されるため型エラーにならない。
名前付き引数
campaignId: 101 のように引数名を明示して渡すPHPの書き方。単純な検索では見つけにくい。
位置引数
引数を順番だけで指定する従来の書き方。
レシーバ
$obj->method() の $obj の部分。どのクラスのメソッドが呼ばれるかは、この変数の型で決まる。
デコイ

幻覚
hallucination。モデルが存在しないファイルや関数を、あたかも存在するかのように出力すること。

1. 検証の設計

4つの軸で比較した。軸1・2はOllama単体で機械的に測定し、軸3・4は専用に作成した合成PHPコードベース（90ファイル、Controller→Model→Logic→Daoのレイヤード構造）上で調査タスクを解かせて採点した。

軸測るもの方法
軸1 生成速度1秒あたりの生成トークン数ollama run --verbose の eval rate
軸2 実用コンテキスト上限100% GPUを維持できる最大コンテキスト長ollama ps の PROCESSOR 列
軸3 ツール呼び出し精度調査の過程（ツール選択・幻覚・完結性）3タスク × 5点満点
軸4 コード調査の精度最終的な結論の正しさ正解セットとの一致度、3タスク × 5点満点

合成コードベースを使った理由は、有名OSSでは学習データ汚染により「調査能力ではなく暗記量」を測ってしまうため。また合成なら正解が設計時点で確定し、デコイ（同名メソッドを持つ別クラス、文字列補間のみの参照など）を仕込んで難易度を制御できる。

  1. 呼び出し元の列挙 — 指定メソッドの呼び出し箇所をすべて特定（正解6件、デコイ7件）
  2. 型変更の影響範囲 — プロパティの型を ?int → string に変えた場合に壊れるファイルを特定（正解7件、デコイ4件、対象外1件）
  3. テスト失敗の原因特定 — 4段の呼び出し連鎖を辿って根本原因を特定

速度の代償は想定より小さい

gemma4:26b の合計所要時間は qwen3-coder:30b の 1.39倍にとどまった。単体プロンプトでの待ち時間比較（29.3秒 対 10.2秒 = 2.9倍）から予測される値より大幅に小さい。

さらに重要なのは、最も難しいタスク2では gemma4:26b の方が高速だった点である（1分35秒 対 1分54秒）。同時に精度は2倍（4/5 対 2/5）だった。qwen3-coder:30b は find | xargs grep による4回の空振り検索と、その後の個別ファイル読み込みに時間を費やしており、雑な調査は速度面でも報われていない。

これは「固定プロンプトでの生成トークン数は、エージェント用途の実所要時間を正確に予測しない」ことの実例でもある。コード生成タスクで冗長だった gemma4:26b（2229トークン）は、調査タスクでは簡潔だった。

qwen3.8:27b は厳密に劣位

gemma4:26b と qwen3.8:27b は両軸で完全に同点（15/15、14/15）でありながら、所要時間は10.2倍の差がある。qwen3.8:27b の32分の大半は、調査そのものではなく「この項目を回答に含めるべきか」という判断の反復に費やされていた。

5. 付随的に判明した技術的事実

アーキテクチャの推定（メモリ帯域からの逆算）

denseモデルは1トークンごとに全重みを読むため、速度上限は「メモリ帯域 ÷ モデルサイズ」で決まる。逆算すると各モデルが要求する帯域は以下になる。

モデル計算要求帯域判定
qwen3.8:27b17GB × 26 tok/s約 442 GB/sM5 Maxの実効帯域と整合 → dense
gemma4:26b17GB × 75 tok/s約 1,275 GB/s物理的に不可能 → MoE（疎）
qwen3-coder:30b25GB × 97 tok/s約 2,425 GB/s物理的に不可能 → MoE（疎）

qwen3.8:27b が同サイズの gemma4:26b の3分の1の速度である理由はこれで説明できる。アーキテクチャ由来の構造的な差であり、設定では埋められない。

thinkingモードの費用対効果

qwen3.8:27b はthinking対応で、既定でONになっている。ollama run --think=false で無効化できるが、Claude Code経由では無効化する経路がない（Anthropic形式のリクエストにOllama独自の think フィールドを載せられない）。

  • thinkingをOFFにしても eval rate はほぼ変わらない（28.70 → 31.41、+9.4%）。thinkingが変えるのは生成トークンの総量（1617 → 1046、−35%）
  • thinkingは CampaignEntryModel の判定を3モデル中唯一正解させるなど、過程の質には寄与した
  • しかし最終スコアは gemma4:26b と同点。thinkingで得られる利点は、thinkingなしの規律ある調査で既に到達可能な水準だった

結論: ローカル環境でthinkingモデルを選ぶ理由は、現時点では見当たらない。

6. ハードウェア投資は解決策になるか

結論: 部分的にしか効かず、モデル間の差は縮まらない。

qwen3.8:27b が10.2倍の時間を要したのは、まったく別の2つの原因が掛け算になった結果である。片方はハードウェアで改善するが、もう片方は一切改善しない。

原因内容速度への寄与ハードウェアで解決するか
アーキテクチャ denseのため、1トークン生成するたびに全重み（17GB）をメモリから読み出す必要がある 約3倍 する（メモリ帯域に比例）
thinkingモード 同じ結論に至るまでに生成する文字数が3〜4倍になる 約3.4倍 しない
3倍 × 3.4倍 ≒ 10倍。実測の10.2倍とほぼ一致する

GPUを強化しても意味がない理由

実測から逆算すると qwen3.8:27b は 17GB × 26 tok/s ≒ 442 GB/s のメモリ帯域を要求しており、M5 Maxの実効帯域（500〜600 GB/s程度）にすでに張り付いている。

つまりボトルネックは演算性能ではなくデータ転送である。GPUは大半の時間、メモリからデータが届くのを待って遊んでいる状態にある。

強化する対象効果理由
メモリ帯域直接効く2倍にすればほぼ2倍速くなる。これがボトルネックそのもの
GPUコア数・演算性能ほぼ無意味GPUは待機しているだけなので、増やしても遊ぶコアが増えるだけ
メモリ容量（VRAM）速度には無関係より長いコンテキストが使えるようになるだけ

参考: データセンター向けGPU（H100は帯域約3.35 TB/s）であれば qwen3.8:27b は6倍前後、150 tok/s程度まで改善すると見込まれる。

それでもモデル間の差は縮まらない

ここが投資判断の分岐点である。メモリ帯域を上げると gemma4:26b も同じように速くなる。 両方が持ち上がるだけなので、10.2倍という比率は保たれる。

さらに原因2（thinkingによる生成量の増加）はどんなハードウェアでも解決しない。ハードを速くすれば1トークンあたりは速くなるが、「3倍の文字数を書く」という性質は変わらないからである。

差を実際に縮める方法は3つしかない。

  1. thinkingを無効化する — ただしClaude Code経由では技術的に不可能（Ollama独自の think パラメータを渡す経路がない）
  2. MoE構造のthinkingモデルを選ぶ — つまり別のモデルに乗り換える
  3. 10倍の待ち時間を受け入れる

モデルの品質と速度は独立した軸である

「新しく高性能なモデルなのだから、速度も同等以上のはず」という直感は成り立たない。

qwen3.8:27b は実際に優れた面を持つ。3モデル中唯一テンプレートトークンの漏れがなく、fd や --no-ignore まで使う調査の徹底性も最高で、CampaignEntryModel の微妙な判定も唯一正解した。1トークンあたりの品質は確かに高い。

しかし品質を上げるための設計選択が、そのまま速度を犠牲にする要因になっている。

  • dense構造を選べば1トークンあたりの計算量が増える（品質は上がりやすいが遅くなる）
  • thinkingを搭載すれば生成量が増える（精度は上がりやすいが遅くなる）

今回の結論は、その犠牲に見合う品質向上が得られなかったということである。gemma4:26b が軸3で15/15、軸4で14/15という満点近くを取ってしまったため、thinkingで伸ばせる余地がほとんど残っていなかった。

7. この検証の限界

  • 合成コードは実プロダクトの癖を再現できない。 命名の不統一、歴史的経緯によるデッドコード、カスタムフレームワーク固有の書き方などは含まれない。順位が実コードでも成立するかは、運用中の観察で確認すべき
  • 規模が実コードより小さい。 90ファイルでは、ファイル数がさらに増えたときに gemma4:26b でも検索が崩れる可能性は排除できない
  • 本番環境で使われている .claude/rules/ のpath-scopedなルール（PHPファイル操作時に自動読み込みされ、アーキテクチャ原則などを与える）を再現していないため、実環境より与えられる文脈が少ない
  • 各タスクは原則1回のみの実施。ローカルLLMの出力揺れは考慮していない
  • 軸1・2の生データファイル benchmark-results-20260826-164643.md は解析バグ修正前に生成されたため、表示が GB 100% GPU / 5571076f3d70 17 のように崩れている（ollama ps の ID 列を考慮していなかったことが原因）。数値自体は正しく、本レポートの値は原本と照合済み
