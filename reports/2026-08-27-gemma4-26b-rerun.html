結論

gemma4:26b を本番モデルとする判断は維持できる。 2026-08-26〜27 の3モデル比較で得たスコアが、独立した再測定でほぼ完全に再現した。

1. 検証の設計

この再測定の目的は、モデルの優劣を新たに決めることではなく、2026-08-26〜27 の3モデル比較で gemma4:26b に付いたスコアが再現するかを確かめることである。ベンチマーク一式は .claude/skills/benchmark-run Skill によって自動実行され、人間の介入は ollama pull の確認のみとした。

4つの軸を次のように測っている。

  • 軸1（生成速度） — 固定プロンプトを4回実行し、1回目（モデルロード直後で不公平）を破棄した3回の eval rate と eval count の平均。
  • 軸2（実用コンテキスト長上限） — 32768 / 65536 / 131072 / 262144 の4段階でサーバーを起動し直し、PROCESSOR が 100% GPU を維持できる最大値を探す。
  • 軸3（調査の過程） — ツール選択2点 / 構文エラーなし1点 / 幻覚なし1点 / 完結性1点の5点満点。
  • 軸4（結論の正しさ） — 最終回答と正解セットの一致度。Recall と誤検出を必ず別々に数える。

対象コードベースは fixture/（PHP合成コード90ファイル）である。実在のOSSを使うと 学習データ汚染で「調査せず記憶で答える」ことが可能になるため、合成コードにしている。 正解セット（answers/）は測定中リポジトリ外へ物理的に退避し、モデルから到達不可能にした。 採点はブラインド採点で行い、モデル名の解決はこのレポート作成時点まで行っていない。

タスクの内容

  1. 呼び出し元の列挙 — Bench\Logic\RewardCalculator::applyBonusRate() の呼び出し箇所をすべて特定する。同名メソッドを持つ別クラス LegacyRewardCalculator（3ファイル）、PHPDocの @see 内の文字列1件、ログイベント名の文字列リテラル1件がデコイ。正解は6ファイル。
  2. 型変更の影響範囲 — UserContext::$campaignId を ?int から string に変えたと仮定し、型エラーまたは明らかな不正動作になるファイルを特定する。campaignId を含む12ファイルのうち、文字列補間のみの参照2件、mixed 引数へ渡すだけの1件、UserContext を参照していない1件がデコイ。正解は7ファイル。
  3. テスト失敗の原因特定 — testBonusAppliedOnCampaignLastDay() の失敗原因を、コードを読んで呼び出し連鎖を追って特定する。正しく実装された同名メソッドを持つ EventPeriodChecker と、無関係なTODOコメントを持つ RankingResetChecker がデコイ。

5. 付随的に判明した技術的事実

アーキテクチャの推定（メモリ帯域からの逆算）

denseモデルは1トークン生成するごとに全重みをメモリから読むため、速度上限は 「メモリ帯域 ÷ モデルサイズ」で決まる。 逆算して SIZE × tok/s を計算し、M5 Maxの実効帯域（500〜600 GB/s程度）と比較する。

コンテキスト長SIZE × tok/s要求メモリ帯域実効帯域比判定
3276817GB × 82.04約 1,395 GB/s2.3〜2.8倍物理的に不可能 → MoE（疎）
6553617GB × 79.55約 1,352 GB/s2.3〜2.7倍同上 → MoE（疎）
13107217GB × 78.27約 1,331 GB/s2.2〜2.7倍同上 → MoE（疎）
26214417GB × 78.00約 1,326 GB/s2.2〜2.7倍同上 → MoE（疎）
 実効帯域比はM5 Maxの実効帯域500〜600 GB/sに対する倍率。4段階すべてで実効帯域を2倍以上超えており、全重みを読んでいない（=MoE）ことの証拠になる

4段階すべてで実効帯域の2倍以上を要求する計算になり、gemma4:26b がMoEであるという推定が 独立した4条件で再確認された。この推定は公式仕様の「25.2B総パラメータ / 3.8Bアクティブ」で裏付けられている。 アクティブパラメータが総パラメータの15%程度であることが、17GBというサイズに対する78〜82 tok/sという速度の説明になる。

実務上の含意として、この速度はメモリ帯域律速ではない。帯域を増やす方向のハードウェア投資で gemma4:26b の速度が比例して伸びることは期待できない。逆に、帯域に張り付いている denseモデル（前回測定の qwen3.8:27b、17GB × 26 tok/s ≒ 442 GB/s）とは投資対効果が根本的に異なる。

thinkingモードの扱い

今回の軸1・2測定は --think を一切指定せず、Ollamaの既定動作で実施した。 --think false との比較は未測定である。 results/ に対応する測定データは存在しないため、thinkingの有無が 今回の eval count（2288〜2585トークン）にどれだけ寄与しているかは切り分けられていない。

前回測定の 2229トークンから今回 2585トークンへ +16% 増えた理由についても、 thinkingの寄与とサンプリングのばらつきを分離できていない。固定プロンプトは同一、測定回数も同一（4回中3回採用）であり、 この差は3回平均のばらつきの範囲内である可能性が高いが、確認するには --think false での再測定が必要である。

6. この検証の限界

  • 軸3の採点が間接評価になっている。 bin/run-tasks.sh は claude -p の 最終出力のみを保存し、ツール呼び出しの経過を残さない。今回の軸3は「結果の正確さ・幻覚の有無・ テンプレートトークンの漏れ・調査の完結性」から間接的に評価した。前回測定で決定的な証拠になった 「rg の結果を | head -20 で打ち切っていた」ような打ち切り・検索パターンの欠陥は、 今回のデータからは検出できない。軸3の満点は「失敗の証拠が無い」ことを意味し、「過程が最適だった」ことは意味しない。
  • 各タスク1回のみの実施。 所要時間はタスク単位で ±20% 動いており（タスク2 +20%、タスク3 −18%）、 スコアについても1回の測定でばらつきの範囲を評価することはできない。今回スコアが前回と完全一致したことは 再現性の証拠になるが、n=2 である。
  • 合成コード90ファイルという規模。 ファイル数が実プロジェクト規模に増えたとき、 gemma4:26b でも検索が崩れる可能性は排除できない。デコイの配置も人為的であり、 実コードの紛らわしさを再現しているとは限らない。
  • コンテキスト長の上限に到達していない。 262144 でも 100% GPU を維持したため、 軸2は「上限が見つからなかった」という結果である。262144 より長い設定は未測定。
  • thinkingの寄与が未分離。 前節のとおり --think false との比較は未測定。
  • 実タスクでの長時間運用は未検証。 今回のタスクはいずれも2分以内に完了しており、 auto-compact が作動する長さのセッションでの挙動は測っていない。
