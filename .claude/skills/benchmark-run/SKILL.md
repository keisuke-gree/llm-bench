# benchmark-run

## 前提

**このSkillは、リポジトリルートで`auto mode`で起動したセッションから実行される
前提です。**

`.claude/settings.json`はルートと`fixture/`の2箇所にあり、役割が正反対である。
`fixture/`側は`allowUnsandboxedCommands: false`でサンドボックスを外す経路が無く、
`ollama`コマンドも外部通信も使えない(測定対象を隔離するため)。ルート側にはこの
制限が無いため、`bin/*.sh`はここから実行する。

**ただし`auto mode`でなければ手順2で失敗する。** `bin/`配下のスクリプトは
`ollama serve`でポートをbind(listen)するが、サンドボックスはbindを拒否する
(`bind: operation not permitted`)。この確認を自動処理させるために`auto mode`が
必要で、設定ファイルでは代替できない(`permissions.defaultMode: "auto"`は
プロジェクトスコープでは付与できない)。起動方法は`README.md`を参照。

**`auto mode`でない場合は、測定を始める前に人間へ伝えて停止すること。**
途中で失敗すると、モデルの切り替えだけが済んだ中途半端な状態が残る。

## 対象の確定(手順に入る前に必ず行う)

**依頼文から対象モデルを読み取って確定させること。** これを曖昧にしたまま
進めると、1モデルだけ測ってほしい依頼に対して3モデル全部を測り、数時間を
無駄にする。

- 依頼文にモデル名(タグ込みの表記。例: `gemma4:26b`)が挙げられていれば、
  **それだけを対象とする。**
- モデル名が一つも挙げられていなければ、既定の3モデル
  (`gemma4:26b`・`qwen3-coder:30b`・`qwen3.8:27b`)を対象とする。
- コンテキスト長が指定されていれば、それだけを対象とする。指定が無ければ
  既定の4段階(`32768`・`65536`・`131072`・`262144`)を対象とする。

確定した対象を、**作業を始める前に「対象モデル: ... / 対象コンテキスト長: ...」
の形で明示して依頼者に見せること。** 意図と違っていればここで止められる。

**引数を省略した`./bin/sweep.sh`は既定の3モデル×4コンテキスト長(12通り)を
測ってしまう。** 対象を絞った場合は、手順2で必ず`--models`/`--contexts`を
付けること。手順4で回すモデルも、ここで確定した集合に限ること。

## 手順

### 1. 前提確認

**`ollama list`を手で叩いて確認してはならない。** このコマンドは`ollama serve`が
起動していないと失敗する。ベンチマーク開始時点でサーバーが動いている保証は無いため、
ここで失敗して手順が止まる。取得済みかどうかの判定はスクリプトに任せる(下記)。

**`ollama serve`を手で起動してはならない。** 素の`ollama serve`はコンテキスト長の
環境変数を受け取らないため、意図しない設定でサーバーが立つ。サーバーの起動は
`./bin/prepare.sh`の責務である(内部で`OLLAMA_CONTEXT_LENGTH`を渡して起動し、
ロード後に`100% GPU`かどうかまで検証する)。

モデルが取得済みかどうかは、`bin/sweep.sh`(手順2)と`bin/prepare.sh`(手順4)の
両方が実行前に確認する。サーバー未起動でも判定できるようディスク上のマニフェストを
見ており、1つでも未取得ならどちらも測定を1件も始めずにエラー終了する。

**未取得と言われた場合、エージェントは`ollama pull`を実行してはならない。**
モデルの取得はネットワークアクセスを伴うため、人間の判断を経る必要がある。
エラーメッセージに出ている`ollama pull`コマンドをそのまま人間に伝えて停止すること。

**`ollama run`は未取得のモデルを自動でダウンロードする。** 上記の確認はそれを
防ぐためのものなので、確認を迂回する経路(手で`ollama run`や`ollama pull`を叩く等)を
作らないこと。

したがってこの手順で行うことは、**対象モデル名を確認するだけ**である。

### 2. 軸1・2の測定

```bash
./bin/sweep.sh
```

**「対象の確定」でモデルまたはコンテキスト長を絞った場合は、引数で明示する。**

```bash
./bin/sweep.sh --models "qwen3-coder:30b" --contexts "131072,262144"
```

複数モデルを指定する場合はカンマ区切りにする。

```bash
./bin/sweep.sh --models "gemma4:26b,qwen3-coder:30b"
```

### 3. 正解セットの退避(**必須**)

```bash
./bin/hide-answers.sh --hide
```

**これを忘れると測定が汚染される。** 手順4(タスク実行)より前に必ず実行すること。

### 4. モデルごとに繰り返す

**「対象の確定」で決めたモデルそれぞれについて**、以下を行う。既定の3モデルを
無条件に回してはならない。

1. `./bin/prepare.sh <model> --force`でモデルを切り替え、サーバーを起動・検証する。
2. 出力の`PROCESSOR`が`100% GPU`でなければ警告する。コンテキスト長を下げて
   `--context-length`付きで再実行するか、人間に判断を仰ぐ。
3. `./bin/run-tasks.sh`でタスクを実行する。対象タスクを絞る場合は`--tasks`を使う。

```bash
./bin/prepare.sh <model名> --force
./bin/run-tasks.sh
```

### 5. 正解セットの復元(**途中で失敗しても必ず実行**)

```bash
./bin/hide-answers.sh --restore
```

手順4の途中でエラーが起きて工程を中断する場合でも、この復元だけは必ず実行すること。
退避したままにすると、手順6(採点)で正解セットを読めず採点できなくなる。

### 6. 採点

`benchmark-score` Skillの手順に従う。**`results/mapping.tsv`を読まないこと**
(ブラインド採点のため)。

### 7. レポート生成

`benchmark-report` Skillの手順に従う。

### 8. 片付け

```bash
./bin/restore.sh
```

`bin/prepare.sh`が起動した`ollama serve`を停止する。

## 必ず守ること

- **依頼文で挙げられていないモデルを測ってはならない。** 「対象の確定」で
  絞った場合、手順2の`--models`と手順4のループの両方に反映すること。片方だけに
  反映すると、軸1・2と軸3・4で対象モデルが食い違ったレポートができる。
- **手順3(退避)を飛ばして手順4を実行してはならない。** `run-tasks.sh`は安全装置として
  退避状態を確認し、退避されていなければエラーで停止するが、これは最後の砦であって
  Skill側でも手順の順序を意識すること。
- **手順5(復元)は、途中で失敗した場合も必ず実行すること。** 退避したままにすると
  採点ができない。手順4で例外的なエラーが発生して工程を中断する場合も、中断する前に
  手順5だけは実行する。
- **採点フェーズ(手順6)に入るまで`answers/answers.md`の内容を読まないこと。**
  読んでしまうとレポート作成者としての客観性が損なわれる。手順3で退避しているため
  物理的にも読めない状態になっているはずだが、`./bin/hide-answers.sh --restore`を
  実行した後(手順5以降)であっても、手順6に入るまでは意図的に読まないこと。
