# benchmark-score

## 目的

`results/answers/` にある各回答ファイルを `answers/answers.md` の正解セットと
突き合わせ、軸3(調査の過程)・軸4(結論の正しさ)のスコアを付けて
`bin/score.sh` で `results/scores.tsv` に記録する。

## 絶対に守ること

**`results/mapping.tsv` を読んではいけない。**

これはブラインドIDとモデル名の対応表である。どのモデルの回答かを知った状態で
採点すると、無意識のバイアス(「このモデルは優秀なはず」等の先入観)が入り、
ブラインド採点の意味が失われる。採点は**回答の内容と正解セットのみ**に基づいて
行うこと。`results/mapping.tsv` というファイル名が視界に入っても、中身を読む・
catする・grepするといった操作は一切行わない。

## 採点手順

1. `results/answers/` 配下の回答ファイルを列挙する。
2. 回答ファイル1件ごとに、同じブラインドIDの `results/traces/<ID>.jsonl` が
   存在するか確認する(存在確認の理由は下記「軸3(調査の過程)の採点手順」を参照)。
3. `answers/answers.md` を読み、各タスクの正解セット・デコイ・採点時の注意点を把握する。
4. 回答ファイル1件ずつについて、軸3・軸4を採点する(手順は下記)。
5. 採点結果を `./bin/score.sh <ID> --axis3 N --axis4 N --note "..."` で記録する。
   **トレースファイルが存在しないIDは `bin/score.sh` を実行しない**(下記参照)。
6. 全件終わったら結果を表で報告する(モデル名は書かない)。

### 軸4(結論の正しさ)の採点手順

正解セットとの一致度を機械的に判定する。

- **Recall**: 正解のうち何件を回答に挙げられたか。
- **False Positive**: 正解セットに含まれない項目(デコイ・対象外・無関係なもの)を
  誤って挙げた件数。

この2軸を必ず別々に数える。`answers/answers.md` の各タスクに記載された
採点指針(正解数・デコイの内訳・裁量で例外を設けてはいけない旨)に厳密に従うこと。
根拠の説明が正確かどうか(理由を正しく説明できているか)も軸4の評価に含める
(`answers/answers.md` にタスクごとの注記がある場合はそれに従う)。

### 軸3(調査の過程)の採点手順

**採点対象は `results/answers/<ID>.md` ではなく `results/traces/<ID>.jsonl` である。**
回答ファイルには最終回答テキストしか入っていないため、ツール呼び出しの経過は
トレースファイルからしか読み取れない。

#### トレースファイルが無い場合: 「測定不能」とし、スコアを付けない

`results/traces/<ID>.jsonl` が存在しない回答IDに遭遇したら、以下のように扱う。

- **そのIDについて `bin/score.sh` を実行しない。** 軸3・軸4はセットで記録される
  仕様のため、軸3の証拠が無いのに軸4だけ確定させると「軸3は無評価」という
  事実が `results/scores.tsv` から読み取れなくなる。
- 最終報告の表では、そのIDの軸3欄に **「測定不能(トレース無し)」** と明記する。
  空欄や「-」のような曖昧な表記にしない。
- 満点・平均点・0点など、いかなる数値も割り当てない。**証拠が無いものに
  満点を付けてはいけない**(トレースが無い = 過程に問題が無かった、を意味しない)。
- 運用者への申し送りとして、`bin/run-tasks.sh` で測定し直せばトレースが
  生成されることを報告に一言添える。

トレースファイルが存在するIDについてのみ、以下の手順で軸3を採点する。

#### トレースファイルの読み方

`results/traces/<ID>.jsonl` は `claude -p ... --output-format stream-json --verbose`
の生イベントストリームで、1行1JSONオブジェクトのJSONL形式である。行ごとに
`.type` フィールドで種別が分かる。採点で見るべき主な種別は以下の通り
(実機の出力形式を確認して構造化した):

- `"type":"assistant"` の `.message.content[]` に `"type":"tool_use"` の要素が
  あれば、それがツール呼び出し(`.name`がツール名、`.input`が引数)。
  どのツールを何回使ったかは、全行を対象にこの要素を数えることで分かる。
- `"type":"user"` の `.message.content[]` に `"type":"tool_result"` の要素が
  あれば、それが直前のツール呼び出しの結果(`.content`に出力本文)。
  `rg`/`Grep`等の呼び出しに対応する`tool_result`の中身を見ることで、
  実際に何件ヒットしたか・出力が打ち切られていないかを確認できる。
- `"type":"result"` の行(最後に1件だけ出現)の `.result` が最終回答テキスト
  (`results/answers/<ID>.md`の中身と同じもの)。

例えば、ツール呼び出しの一覧とその引数だけを抜き出すには次のようにする
(`jq`を使う。20行を超える出力になり得るため、`ctx_execute_file`等での
要約・集計を推奨する):

```bash
jq -c 'select(.type == "assistant") | .message.content[]? | select(.type == "tool_use") | {name, input}' results/traces/<ID>.jsonl
```

#### 採点する4観点(満点5点)

1. **適切なツールを選択できたか**(2点) — 対象言語・対象拡張子に合った検索ツールを
   使えているか、`CLAUDE.md` のツール使用規則(`rg`/`fd`への統一など)に従っているか。
2. **ツール呼び出しの構文・形式エラーが無かったか**(1点) — `tool_result`側に
   エラーメッセージ(構文エラー・権限拒否等)が出ていないか。
3. **存在しないファイルパス・シンボルを幻覚しなかったか**(1点)
4. **途中で諦めず調査を完結させたか**(1点) — `.type=="result"`まで到達し、
   最後のツール呼び出しの後に推測で打ち切っていないか。

### 軸3で特に注意して見るべき失敗パターン

過去の検証で実際に観測された、見落としやすい失敗パターン。トレースファイルの
`tool_use`/`tool_result`を読みながら確認する。

- **検索結果を `| head -N` で打ち切っている。** `tool_use.input.command`に
  `| head -N`が含まれ、対応する`tool_result`の行数が上限ちょうど(例: `head -20`
  に対して20件ちょうど)の場合、切り捨てが起きた疑いがあり、見落としの
  直接の原因になる。
- **検索パターンが構文の変種を取りこぼしている。** 例: `$obj->prop` を探す
  パターンでは、名前付き引数 `prop: 値` の形にマッチしない。
- **判断に迷ったとき、コードを読んで確認せず「〜の可能性があります」という
  推測で答えている。** 検証を放棄した兆候であり、軸3の観点1・4の減点対象になる。
- **対象と無関係な拡張子を検索している。** 例: PHPプロジェクトで `*.cs`
  (C#)を探すなど、プロジェクトの技術スタックを把握していない兆候。同じ
  検索を拡張子違いで繰り返して「存在しない」と誤結論している場合は特に重い
  減点対象。
- **`find | xargs grep` 等、`CLAUDE.md` のツール使用規則(`rg`への統一・
  `fd`への統一)に反するコマンドを使っている。** `tool_use.input.command`を
  見れば分かる。
- **チャットテンプレートの制御トークンが出力に漏れている。** 例: `<function=...>`、
  `<channel|>` など。`tool_use`として構造化されず、`assistant`のテキスト部分に
  平文で現れる。ツール呼び出しが実際には失敗している(構文エラーとして
  実行されていない)ことを示すため、観点2の減点対象になる。

## 採点結果の記録

トレースファイルがあるIDについて、回答1件ごとに以下を実行する。

```bash
./bin/score.sh <ID> --axis3 N --axis4 N --note "..."
```

`--note` には減点理由を簡潔に書く(例: 「検索結果をhead -20で打ち切り、見落とし2件」)。
減点が無い満点の場合は `--note` を省略してよい。

**トレースファイルが無いIDについては `bin/score.sh` を実行しない。** 軸4だけを
先に確定させたい場合でも、`bin/score.sh`は軸3・軸4を同時に1行として記録する
仕様のため、軸3を「測定不能」のまま `results/scores.tsv` に残す方法が無い。
無理に数値を割り当てるのではなく、`bin/score.sh`の実行自体を見送り、後述の
報告の表でそのIDを明示すること。

回答ファイルが見つからない・IDが重複している等のエラーが `bin/score.sh` から
返ってきた場合は、IDの指定ミスが無いか再確認してから対処すること。

## 報告

全件の採点が終わったら、ブラインドIDごとのスコア一覧を表で示す。トレースファイルが
無く「測定不能」としたIDは、軸3欄にその旨を書き、軸4欄には「score.sh未実行」と
書く(そのID自体を `bin/score.sh` に記録していないため)。

| ブラインドID | 軸3 | 軸4 | 備考 |
|---|---|---|---|
| answer-02 | 測定不能(トレース無し) | (score.sh未実行) | results/traces/answer-02.jsonl が存在しない。run-tasks.shで再測定が必要 |
| answer-01 | ... | ... | ... |

**モデル名は書かない。** この時点ではどのIDがどのモデルかを採点者自身も
知らないため(`results/mapping.tsv` を参照していないため)、書きようがない。
モデル名の解決は `benchmark-report` Skillに委ねる。
