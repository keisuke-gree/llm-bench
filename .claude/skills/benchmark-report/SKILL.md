# benchmark-report

## 手順

1. `./bin/new-report.sh <スラグ>` でレポートファイルを生成する
   (`reports/YYYY-MM-DD-<スラグ>.html`)。
2. `results/` から必要なデータを集める。
   - `results/benchmark-results-*.md`(軸1・2の測定値。複数ある場合は最新のものを使う)
   - `results/scores.tsv`(軸3・4のスコア。ブラインドIDのまま記録されている)
   - `results/mapping.tsv`(ブラインドIDとモデル名・コンテキスト長・タスク番号の対応表)
3. `results/mapping.tsv` でブラインドIDをモデル名に解決する。
   **このSkillでは対応表を参照してよい。** `benchmark-score` Skillでの採点が
   完了した後であり、モデル名を知っても採点結果に影響しないため。
4. **同じ(モデル, タスク番号)の組が複数ある場合は、中央値を代表値にする。**
   モデル間比較では各タスクを3回実施するため、1モデル1タスクにつき3件の
   ブラインドIDが対応する(下記「複数回測定の集計」を参照)。
5. 生成したレポートファイルのプレースホルダを埋める(`{{MODELS}}` /
   `{{AXIS12_TABLE}}` / `{{AXIS34_TABLE}}` / `{{WAITTIME_TABLE}}`。
   `{{TITLE}}` と `{{DATE}}` は `bin/new-report.sh` が既に埋めている)。
6. 分析セクションを書く(下記の「必ず行う分析」に従う)。

## 必ず行う分析(今回の検証で確立した手法)

### アーキテクチャの推定(メモリ帯域からの逆算)

denseモデルは1トークン生成ごとに全重みをメモリから読むため、速度上限は
「メモリ帯域 ÷ モデルサイズ」で決まる。逆算して `SIZE × tok/s` を計算し、
実機の実効メモリ帯域(Apple Silicon M5 Maxで500〜600 GB/s程度)と比較する。

- 実効帯域と概ね一致する → **dense**(帯域律速。物理的な上限に張り付いている)
- 実効帯域を大きく超える(2倍以上) → **MoE**(全重みを読んでいない証拠)

この推定は実際に的中した実績がある(`gemma4:26b` を17GB × 75 tok/s = 約1,275
GB/s から MoE と推定し、後に公式仕様の「25.2B総パラメータ / 3.8Bアクティブ」で
裏付けられた)。SIZEと`tok/s`が揃っているモデルすべてについてこの逆算を行い、
判定結果を表にまとめること。

### 実際の待ち時間の算出

`eval rate`(生成速度)だけを見て速度を評価してはいけない。`eval count`
(生成トークン数)と掛け合わせて「実際の待ち時間 = eval count ÷ eval rate」を
必ず算出し、`{{WAITTIME_TABLE}}` に含めること。

過去に `eval rate` だけを見て誤った推奨をした事例がある。速度差22%のモデルが
生成量2.3倍だったため、実際の待ち時間は2.9倍だった。**冗長なモデルは高速でも
体感が遅い。** この非対称性が今回の検証にも当てはまるかを必ず確認する。

### 複数回測定の集計

モデル間比較では各タスクを3回実施するため、`results/mapping.tsv`上で同じ
(モデル, タスク番号)に3件のブラインドIDが対応する。

- **代表値は中央値を使う。平均は使わない。** 1回だけ検索範囲を誤るといった
  外れ値に引きずられるため。
- 表には中央値を載せるが、**3回のばらつきも必ず併記する**(例:
  `4/5 (5,4,4)`)。ばらつきを隠すと、次に読む人が1回の測定と同じ重みで
  受け取ってしまう。
- **中央値の差が1点しかないモデル同士を「優劣あり」と書かない。**
  過去に1モデルで軸4が14→12まで振れた実測があり、この幅はモデル間の差として
  扱っていた幅と同程度である。差が小さい場合は「判定できない」と書くこと。

同じ(モデル, タスク番号)が1件しか無い場合は単一モデルの追試であり、
その旨をレポートに明記した上でスコアをそのまま載せる。

### 軸3と軸4を分けて論じる

軸3(調査の過程)のスコアが同じでも、軸4(結論の正しさ)は問題の難易度によって
大きく変わる。過去の測定では、易しいタスクでは過程が雑でも結論が当たり
(5/5)、判断を積み重ねる難しいタスクで崩れた(2/5)。**過程の質は問題が
易しいうちは結果に表れない**という性質を踏まえて考察すること。タスクごとの
難易度差(単純な検索か、多段階の判断が必要か)を明示し、軸3と軸4のスコアの
乖離が大きいタスクがあれば、その原因を回答内容から特定する。

### thinkingモードの扱い

thinking対応モデルを含む場合、`eval rate` はthinkingの有無でほとんど
変わらないが `eval count` は大きく変わることに注意する。`sweep.sh --think
false` との比較データが `results/` にあれば併記する。無い場合は「未測定」と
明記し、推測で埋めない。

## レポートに含めるべきセクション

`_template.html` の構成に対応する形で、以下を含める。

- 結論(推奨モデルとその根拠)
- 検証の設計
- 軸3・4のスコアと考察
- 所要時間
- 軸1・2の測定値
- 付随的に判明した技術的事実
- この検証の限界
- 推奨アクション

## 体裁のルール

- **専門用語にはホバー説明を付ける。** 本文中は `<span class="t"
  data-tip="...">` を使い、表のセル内は `title` 属性を使う(表は
  `overflow-x: auto` の中にあるため、CSSの吹き出しは切り取られる)。
  `_template.html` に用語集と機構が用意されているので流用し、今回の検証固有の
  用語があれば用語集の `<dl>` に追加する。
- **同じ用語は最初の出現箇所だけに付ける。** 2回目以降の出現にはツールチップを
  付けない。
- **「◯月◯日追記」「旧版では〜」のような編集過程を説明する記述を書かない。**
  読み手には無意味な情報である。修正後の状態だけを書く。ただし証拠の取得時期を
  示す日付(「2026-08-12実測」等)は情報の鮮度を判断する材料なので残してよい。
- **測定していない値を推測で埋めない。** データが無い項目は「未測定」と
  明記する。
